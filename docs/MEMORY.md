# Память и бюджеты (S4-08, S5-14, S5-32, S7-09)

Бюджет — `docs/HANDOFF.md` §2c: ≤ 150 МБ рабочего набора с открытым ящиком 50 тыс. писем и календарём. Здесь — что
держит память, что исправлено и что осталось.

## Как мерить

```
cargo build --release -p postman-gpui -p postman-worker
target\release\postman.exe --demo 50000 --bench                 # строка key=value; Git Bash ждёт выхода сам
```

Поля памяти в строке бенча:

| Поле | Что это |
|---|---|
| `rss_peak_mb`, `private_peak_mb` | пик рабочего набора и private bytes за сценарий (выборка раз в 20 кадров) |
| `rss_<фаза>_mb`, `private_<фаза>_mb` | на границах фаз: `start` — после прогрева (окно открыто, письмо не открыто), `scroll` — после листания с открытием писем, `list` — после листания списка, `resize` — после ресайза |
| `idle_rss_mb`, `idle_private_mb` | после сценария и 13 с простоя — **это число сравниваем с бюджетом** |
| `idle_private_ws_mb` | частный рабочий набор: столбец «Память» диспетчера задач (без разделяемых страниц DLL) |
| `heap_live_mb`, `heap_peak_mb`, `heap_blocks` | куча Rust (живые байты, пик, блоки) — только в сборке `--features alloc-count` |

Разбивка и отдельные фазы:

```
set POSTMAN_BENCH_MEMMAP=1                    # в stderr: образы по модулям, файлы, блоки частной памяти (как VMMap)
cargo build --release -p postman-gpui --features alloc-count   # поля heap_… (считающий распределитель)
set POSTMAN_BENCH_SCROLL_FRAMES=0             # фазы по отдельности: 0 кадров — фазы нет
set POSTMAN_BENCH_LIST_FRAMES=0
set POSTMAN_BENCH_RESIZE_FRAMES=0
set POSTMAN_BENCH_MAX_IDLE_RSS_MB=150         # порог: idle_rss_mb выше — stderr и код выхода 1
set POSTMAN_BENCH_IDLE_LIFECYCLE=1            # простой с планировщиком сроков (S5-14)
set POSTMAN_BENCH_IDLE_OFFLINE=1              # простой «нет связи» с отсчётом повтора (S5-14)
set POSTMAN_BENCH_IDLE_SECTION=tasks          # простой в разделе: calendar, contacts, tasks (S5-32)
```

Память GPU процесса (на встроенной графике она в памяти процесса, см. ниже) — счётчики Windows, без прав
администратора: `Get-Counter "\GPU Process Memory(pid_<PID>*)\Shared Usage"`, пока идёт бенч.

Сборку с `alloc-count` и опыты — в отдельный каталог (`CARGO_TARGET_DIR=target\s408-prof`), чтобы не пересобирать
общий `target\release`.

## Стенд замеров

Ноутбук владельца, Windows 11, **Intel Graphics (встроенная, общая память)**, монитор 2560×1440, масштаб 125 % —
окно бенча 1280×800 = 1600×1000 пикселей устройства; 144 Гц, от сети. Демо 50 тыс. писем, release.

На встроенной графике текстуры и буферы D3D — память процесса (растут private bytes и рабочий набор вместе со
счётчиком `GPU Process Memory\Shared Usage`). На дискретной (RTX 5060 в `docs/STALWART.md`) их нет в рабочем
наборе — там числа будут ниже; сравнивать замеры только на одной машине.

Не в демо: индекс поиска tantivy (писатель открывается лениво с кучей 15 МБ и закрывается после коммита — S3),
runtime tokio и поток синхронизации, адресная книга сервера — только у живого ящика; живой замер (`--bench --live`)
нужен стенд [проверить]. Календарь (демо-неделя) создаётся при старте и входит в замер, но его экран бенч не
открывает — глифы и раскладка недели в атлас не попадают [проверить отдельным замером]. Окна письма и встречи держатся через `WeakEntity`: закрытое окно освобождается; каждое
открытое окно — свой swapchain; текстур путей (окно письма 1025×850 — ещё ~17 МБ) после патча gpui нет.

## Исправлено (S4-08)

- **Картинки закрытого письма убираются из атласа** (`app-gpui/src/reading.rs`): при смене или закрытии письма его
  картинки уходят в `retired`, при следующей отрисовке области чтения — `window.drop_image`. Память больше не растёт
  с числом открытых писем с картинками.
- **Кэш redb 16 → 4 МБ** (`crates/cache/src/lib.rs`): кадр листания не изменился (p99 8,1–8,7 мс до и после).
- Бенч: память на границах фаз, `idle_private_ws_mb`, порог `POSTMAN_BENCH_MAX_IDLE_RSS_MB`, разбивка
  `POSTMAN_BENCH_MEMMAP`, фича `alloc-count`, число кадров ресайза `POSTMAN_BENCH_RESIZE_FRAMES`; фазы с нулём кадров
  закрываются правильно.

`EmptyWorkingSet`/`SetProcessWorkingSetSize` не применяем: они уменьшают рабочий набор, но не private bytes —
страницы вернутся при первой отрисовке; это подгонка числа, а не экономия.

## Что осталось против бюджета

С патчем gpui (pets #13) простой — **98–106 МБ**, пик — **105–115 МБ**, ресайз памяти не добавляет: бюджет ≤ 150 МБ
выполнен с запасом ~45 МБ. Остаток — образы exe и DLL (~49, почти всё разделяемые), прочее GPU и DirectWrite (~30),
куча Rust и кэш redb. Upstream — предложить ленивые текстуры путей в zed-industries/zed (`gpui_windows`).

Если патч придётся откатить («Если что откатим» — владелец, 2026-10-21): rev `pets` назад на `a536836`, простой
вернётся к 128–159 МБ, пик — к 189–227 МБ.

Шумные прогоны (загрузка 52–93 %, сборки других агентов): листание p99 10–25 мс, первый кадр до 1,6 с — машина, не
Postman: на тихой те же сборки дают 8,3–8,8.

**Что проверено отдельно.**

- **Простой с фоновыми частями.** Бенч по умолчанию простаивает без планировщика жизненного цикла (повторяемость), а
  связь у демо всегда есть, — то есть таймеры S5 в простое не мерились. Два ключа бенча включают их в начале простоя:
  `POSTMAN_BENCH_IDLE_LIFECYCLE=1` (проход по ящику и таймер к ближайшему сроку) и `POSTMAN_BENCH_IDLE_OFFLINE=1`
  («нет связи», повтор через 60 с — как наибольшая пауза синхронизации). Планировщик: таймер один, к ближайшему
  сроку (`arm_lifecycle`, срок тот же — таймер прежний), проход — в фоне; простой не изменился.
- **Регрессия: отсчёт «Нет связи · повтор через N с»** будил окно раз в секунду всё время без связи (и в попытке
  «подключение…», когда число не меняется): каждый тик — перерисовка экрана почты, +0,1–0,6 % ядра. Исправлено
  (`states.rs`): таймер ставится к следующей смене числа (`Offline::next_change`), последние 10 с — по секунде,
  раньше — шагом 5 с вверх («через 60 с», «55 с»…), в попытке таймера нет; цикл 60 с — 20 перерисовок вместо 60.
- **Счётчики быстрых фильтров** (`MailList::recompute`, проход по папке в фоне) — только по событиям: смена
  фильтров, папки, данных (`refresh` после синхронизации и правок), вида беседы; из `render` не зовутся. Кадр листания
  их не запускает.
- **Палитра** строит список команд, папок и фильтров при открытии (Ctrl+K), письма — с паузой 150 мс после ввода;
  закрытая палитра ничего не держит. Тосты — таймер раз в секунду («N с» и уход по времени), только пока они на экране.
- **Кэш view.** Все части экрана, которые меняются сами (список, папки, чтение, командная строка, фильтры, сводка,
  вкладки письма и настроек, календарь, контакты, палитра), встроены через `.cached(...)`; `ui_cpu_p50` 0,1 мс —
  экран почты при листании не перестраивается. Закладки быстрых фильтров и тосты рисует сам экран почты — по своим
  событиям (`observe` фильтров, таймер тостов), не каждый кадр.
- **Пик памяти +15 МБ** (105–115 → 119–131) — рабочий набор при листании с открытием писем (`rss_scroll_mb` 108–127):
  простой — прежний, бюджет — с запасом 19 МБ. Причину не разбирали [проверить `POSTMAN_BENCH_MEMMAP=1`: вероятно,
  атлас глифов и кадров интерфейса S5 — ленты вложений, метки, беседы в области чтения].

**Новый ключ бенча.** `POSTMAN_BENCH_IDLE_SECTION=calendar|contacts|tasks` — в начале простоя открыть раздел: его
таймеры (напоминания задач, поиск календаря, ожидание занятости) и перерисовки попадают в `idle_cpu_pct`.

**Что проверено.**

- **Таймеры новых частей** — по одному к ближайшему сроку и только по событию: напоминания задач (`remind_pass`, не
  чаще раза в сутки без сроков), уход выполненной задачи через 2 с, сохранение заметок через 0,8 с после ввода,
  KeyTips (одно пробуждение на удержание Ctrl), автосохранение письма — только после правки, поиск календаря и занятость
  встречи — пауза после ввода. Кадров по кругу нет: простой с открытыми «Задачами», «Календарём» и «Контактами» —
  0,0–0,2 %, как «Почта».
- **Кэш view.** Новые разделы (`tasks`, `tasks_bar`) встроены через `.cached(...)`, как календарь и контакты.
- **Память в простое +8 МБ** (98–107 → 107–112): разбивка `POSTMAN_BENCH_MEMMAP=1` — образ `postman.exe` в рабочем
  наборе 8 → 11 МБ (код S5/S6 +4,6 МиБ), частная память 50–61 → 58 МБ (кучи и атлас интерфейса новых частей); образы
  драйвера и системных DLL — прежние 50 МБ. Бюджет — с запасом 38 МБ.
- **Пик +10 МБ** (до 141): рабочий набор при листании с открытием писем (`rss_scroll_mb` 111–137) — карточки
  приглашений Г1, подписи S/MIME и ленты вложений в области чтения; запас до бюджета — 9 МБ в худшем прогоне.

**Что не исправлено (не локальная правка).**

- **Поток интерфейса при листании с открытием писем 52–63 → 54–86 % ядра** (медиана 77), при том что построение кадра
  (`ui_cpu_p50` 0,13 мс) почти прежнее и кадры успевают в vsync: рост — раскладка и отрисовка gpui (prepaint, paint,
  текст) более тяжёлой области чтения, а не `render` своих view. Разбор — профилировщиком (ETW / `samply`) против
  сборки S5-14 на открытом столе [проверить]; без него не видно, какая часть экрана.
- **Без связи 0,2–0,6 %** (было 0,0–0,3): в 10 с простоя 2–3 смены числа «повтор через N с», каждая — перерисовка экрана
  почты (дочерние view закэшированы, перекладывается и рисуется каркас окна). Около предела; вынести строку состояния
  в свою кэшируемую view — отдельной правкой, если выбросы повторятся на открытом столе.
- **Один прогон из 36 — `idle_cpu_pct` 44,2** (≈ 4,4 с CPU за 10 с простоя). Не повторился в 35 прогонах, в том числе
  в 15 подряд обычных; совпал с блокировкой рабочего стола и загрузкой машины 28 % [проверить на открытом столе:
  `POSTMAN_LOG=debug` и стек потоков в Process Explorer во время простоя].
