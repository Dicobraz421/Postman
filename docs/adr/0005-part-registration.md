# ADR 0005. Сцены, команды и тексты регистрирует модуль части

Статус: **предложено** (2026-10-26, R-05 перевода на pets-dev, `pets/skills/pets-dev/rollout/postman.md`). Решает
владелец; после принятия — волна полосы интерфейса (план ниже). До принятия код не меняется.

Образец — ADR-0022 Урфина (`Dicobraz421/Urfin`, `docs/adr/0022-feature-registration.md`): списки явные, по строке на
фичу, без новых зависимостей. Принцип тот же, что у ADR 0004 («ядро функциональное, протоколы — плагины»): новое
подключается своим модулем и одной строкой в композиционном корне, а не правкой центральных файлов.

## Разведка

Последние 40 коммитов каждого горячего файла `app-gpui/src` (`git log -p -U0`, добавленные строки по шаблонам):

| Файл | Коммитов всего | Строк | Что повторяется (коммитов из 40 / добавлено строк) |
|---|---:|---:|---|
| `screens.rs` | 50 | 1973 | новая сцена: вариант `enum Scene` (36 / 87), строка в `SCENES` (36 / 90), имя в `Scene::name` (36 / 92), ветки `enter`/`ready`/`continues` (36 / 222); сброс «только в своей сцене» `matches!(scene, …)` в `enter` (15 / 19) |
| `main.rs` | 51 | 429 | строка `mod x;` (35 / 63), пара `("ru"/"en", include_str!(…ftl))` в `TEXTS` (22 / 50), флаги запуска (8 / ~46) |
| `mailer.rs` | 42 | 972 | `.on_action(…)` в `render` (25 / 86), оверлеи и дети `.child(…)` (13 / 53), поля `Mailer` под фичу (11 / 16) |
| `commands.rs` | 39 | 733 | `cmd("…")` в `COMMANDS` (30 / 153), `actions!` и `pub mod <область>` (24 / 31; 11 / 15), id команд в тестах и таблицах (33 / ~196) |

Итог: из последних 71 коммита, тронувших эти файлы, 49 правят два и больше из них, 24 — все четыре. Новая фича
почти всегда правит одни и те же места: сцена (4 места в `screens.rs`), тексты и `mod` (`main.rs`), команды
(`commands.rs`), обработчики (`mailer.rs`). Отсюда конфликты параллельных волн и чтение файлов в 1–2 тыс. строк целиком.

Уже есть зачаток нужного: `actions::handlers` и `attachments::handlers` вешают свои `on_action` из своего модуля
(`mailer.rs` только сцепляет их), тексты разложены по файлам части (`i18n/<язык>/<часть>.ftl`).

## Решение (предложение)

### Часть — модуль с одной описью

Часть интерфейса (вложения, задачи, контакты, S/MIME, поиск…) — модуль, который отдаёт одну константу:

```rust
// app-gpui/src/part.rs — тип описи (имя `Feature` занято: `postman_core::model::Feature` — умения сервера)
pub(crate) struct Part {
    pub name: &'static str,                                  // для журналов и тестов
    pub texts: &'static [pets_i18n::Resource],               // свои .ftl, RU и EN
    pub commands: &'static [pets_commands::Command],         // свои cmd(…) с клавишами и контекстом
    pub handlers: fn(Div, &mut Context<Mailer>) -> Div,      // свои on_action (как actions::handlers сейчас)
    pub scenes: &'static [screens::Scene],                   // свои сцены --screens, в порядке съёмки
    pub reset: Option<fn(&mut Mailer, &mut Window, &mut Context<Mailer>)>, // чистое начало сцены для своего состояния
}

// в модуле части, например tasks.rs
pub(crate) const PART: Part = Part { name: "tasks", texts: TEXTS, commands: COMMANDS, handlers, scenes: SCENES, reset: None };
```

- **Действия** (`actions!`) — в модуле части (`tasks::cmd`), пространство имён прежнее (`task::New`), id команд и
  клавиши не меняются.
- **Сцена** — значение, а не вариант общего перечисления:
  `Scene { name, set: Demo | Live | SignIn, continues: bool, enter: fn(…) -> Result<(), String>, ready: fn(…) -> bool }`.
  Шаги `enter`/`ready` переезжают из `screens.rs` в часть; `screens.rs` остаётся двигателем (кадры, ожидание,
  снимок, таймауты, `clean_slate`). Сброс «только в своей сцене» — в `reset` части, владеющей состоянием.
  «Продолжает прошлую» — только сцену, стоящую перед ней в том же списке части.
- **Оверлеи и поля `Mailer`** — не в первой волне: правок меньше (13 и 11 из 40). Позже — `overlay: Option<fn…>` в
  `Part` по образцу Урфина.

### Сборка — одна строка на часть

`app-gpui/src/parts/mod.rs` — единственное место, где появляется новая часть: `pub(crate) mod tasks;` и
`tasks::PART,` в `pub(crate) const PARTS: &[Part]`. Порядок `PARTS` — порядок сцен, клавиш и проверки команд.
`main.rs` один раз получает `pub(crate) use parts::*;` (пути `crate::tasks::…` не меняются) и больше части не знает.

Из `PARTS` собираются:

- тексты — `pets_i18n::init` уже принимает список срезов: `PARTS.iter().map(|p| p.texts)` плюс `pets_ui::FTL`;
- команды — `LazyLock<Vec<Command>>` (срезы склеиваются один раз при запуске; `pets_commands::{find, validate}`,
  `keymap::bound`, палитра, `PARITY.md` и `keys.md` берут `&COMMANDS[..]` как сейчас);
- обработчики — `PARTS.iter().fold(div(), |d, p| (p.handlers)(d, cx))` в `Mailer::render`;
- сцены — `PARTS.iter().flat_map(|p| p.scenes)` с фильтром по `set` (вместо `SCENES`, `LIVE_SCENES`, `SIGNIN_SCENES`).

Общий код, который не часть (рамка, вкладки, рейл, `mailer.rs`, двигатель снимков, `commands::bind`), остаётся где
есть. Новая часть правит: свой модуль, свои `.ftl`, две строки в `parts/mod.rs`. Такая правка конфликтует редко и
сливается механически.

### Проверки

Тест `parts`: имена сцен уникальны, у каждой части тексты на RU и EN, `continues` не стоит первой в части. Тесты
`commands` (уникальность id, ключи `.ftl`, `PARITY.md`) и `pets_i18n::check` работают по собранным спискам без
изменений смысла.

## Варианты механизма

| Вариант | Плюсы | Минусы |
|---|---|---|
| **Явные `const`-описи + `PARTS`** (выбран) | без зависимостей; порядок задан (сцены продолжают друг друга, клавиши проверяются по порядку); всё видно поиском; одинаково с Урфином (ADR-0022) | одна строка на часть в `parts/mod.rs` — всё же общий файл, но правка в одну строку |
| `linkme` (`#[distributed_slice]`, MIT/Apache) | ни одной общей строки | порядок элементов не определён — сценам и клавишам нужен порядок, придётся сортировать по ключу; секции компоновщика на MSVC — источник редких поломок; `mod x;` всё равно нужен |
| `inventory` (MIT/Apache) | ни одной общей строки | регистрация в конструкторах до `main` (`ctor`), порядок не определён, `const` не годится — списки строятся в рантайме; та же оговорка про `mod x;` |

Рекомендация — **явные описи**: выигрыш `linkme`/`inventory` — одна строка `PART,` рядом с обязательной строкой
`mod`, а цена — неявный порядок и зависимость. Новые крейты не нужны, `Cargo.toml` не меняется.

## План волны (после принятия ADR; полоса интерфейса, PR по одному)

1. **Опись и сборка.** `part.rs`, `parts/mod.rs`, `PARTS` с одной частью `legacy` (нынешние `TEXTS`, `COMMANDS`,
   обработчики `mailer.rs`); `main.rs` и `commands.rs` берут списки из сборки. Поведение и `--screens` — без изменений.
2. **Сцены.** `enum Scene` → `struct Scene`; `SCENES`/`LIVE_SCENES`/`SIGNIN_SCENES` — из `PARTS`; `continues`
   и сбросы в `enter` — полями сцены и `reset`. Сверка: те же имена и снимки, что до волны.
3. **Перенос частей** (2–3 PR, сначала с готовыми `handlers`): вложения, действия, задачи, контакты, календарь и
   встречи, S/MIME, поиск и палитра, настройки. Модули — в `src/parts/` (`git mv`), их `cmd(…)`, `actions!`, `.ftl`,
   `on_action` и сцены — в свою опись; `legacy` худеет до общего.
4. **Правило в доках.** `CLAUDE.md`/`docs/DEV.md`: «новая часть — модуль в `parts/` + две строки в `parts/mod.rs`»;
   `files` карточек и `lanes.toml` — по новым путям.

Каждый PR: fmt, clippy, тесты `postman-gpui`, `--screens` dev-сборкой со сверкой с эталоном.

## Последствия

- Межкрейтовые контракты не меняются: всё внутри `app-gpui`.
- Риск — регрессии сцен (порядок, сбросы состояния между сценами); ловит сверка `--screens` на шагах 2–3.
- Вне ADR остаются флаги запуска `main.rs` (8 из 40 правок) и оверлеи/поля `Mailer` — вернуться, если станут горячими.

## Откат

Сборка из описей механически сворачивается обратно в центральные списки: id команд, ключи текстов и имена сцен
не меняются.
