# ADR 0006. Единое хранилище: письмо — строка метаданных, содержимое — по хэшу

Статус: **принято** (владелец, 2026-10-28; S8, `docs/specs/S8.md`). Требование владельца 2026-10-28 —
`docs/decisions/2026-10-28-v1-requirements.md` п. 1. Меняет формат кэша (`crates/cache`), договор команд и событий
(`postman_core::sync`, `model`) и работу плагинов с ключами писем; правило ADR 0004 «новая функция может расширить
ядро» — перенос между учётными записями и выгрузка на сервер становятся функциями ядра.

⚠ отступление от прежнего правила кэша: «хранилище одноразовое, при смене формата пересоздаётся» (`crates/cache`
`//!`) — с локальными архивами в базе есть данные, которых нет на сервере; формат меняется только миграцией.

## Как сейчас

- **Файл на профиль.** Кэш — один файл redb на основную учётную запись (`account-<логин>-<хэш>.redb`,
  `app-gpui/src/account.rs`); дополнительные учётки профиля (S7-03б) и общие ящики живут в нём же под префиксом
  ключа: `@2/<id>`, `<аккаунт>/<id>`, `@2.<аккаунт>/<id>` (`postman_cache::scoped`, `in_profile`).
- **Ключ письма = учётка + id сервера.** Ключ строки `email` — `scoped(аккаунт, id сервера)`; у IMAP в id входит
  путь папки (T1-04в: после `RENAME` ключи папки и писем переписываются). Маршрут команды к потоку учётки —
  по префиксу ключа (`Command::routes`). Перенос между учётками сейчас невозможен без смены ключа.
- **Таблицы:** `email` (строка списка), `by_mailbox` `(папка, −дата, id)`, `count`, `by_keyword`,
  `keyword_count`, `by_thread`, `recipients`, `body` (разобранные HTML и текст + список вложений), `blob` (по id
  блоба сервера, до 16 МиБ), `smime`, `smime_certs`, `task`, `sync_state`, `account`, `mailbox`.
- **Письмо целиком** есть не у всех: IMAP и EWS кладут RFC 5322 в `blob` под ключом письма; JMAP берёт у сервера
  `bodyValues` (MIME разбирает сервер), письмо целиком — только для проверки S/MIME.
- **Одноразовость.** `FORMAT_VERSION` не совпал — файл удаляется и наполняется синхронизацией: главная копия — на
  сервере.
- **Шифрование хранения.** Своего нет: файл в `%LOCALAPPDATA%\Postman` под ACL профиля Windows, диск — BitLocker,
  если его включила организация. Письмо S/MIME хранится только зашифрованным блобом; расшифрованный текст и ключ
  содержимого — в памяти на сеанс, в поиск не попадают (`docs/SMIME.md` §8, решение №4). Пароли — Credential
  Manager. Шифрование хранения Stalwart — на стороне сервера (`docs/SMIME.md` §9).

## Решение

### 1. Письмо — строка метаданных с локальным id

- **`LetterId`** — `u64`, выдаётся счётчиком `meta.next_letter` и не меняется никогда: ни при переносе между
  папками, ни между учётками, ни при выгрузке на сервер. Интерфейс и поиск работают с ним.
- **Строка письма** `letter: LetterId → LetterRow` — то же, что `EmailRow` сейчас (тема, отправитель, дата,
  превью, флаги, ключевые слова, размер), плюс:
  - `folders: Vec<FolderId>` — членство в папках; это изменяемое поле, у JMAP папок может быть несколько;
  - `content: Hash` — письмо целиком (п. 2); `None` — ещё не загружено с сервера;
  - `place: Place` — `Synced` (есть на сервере своей учётки), `Local` (только в базе), `Outbound(JobId)`
    (переносится, п. 4).
- **Связь с сервером** — отдельно: `remote: (AccountKey, id сервера) → LetterId` и обратная
  `letter_remote: LetterId → Vec<RemoteRef>` (`RemoteRef` — учётка, id сервера и что нужно протоколу: IMAP —
  папка + `UIDVALIDITY` + UID, EWS — `ItemId` + `ChangeKey`, JMAP — `Email.id`). Это таблица `remote` из ADR 0003
  («Идентификаторы»), до сих пор не сделанная. Плагин пишет и читает письма через неё: `upsert_remote(учётка, id,
  строка) → LetterId`.
- **Папки** — `folder: FolderId → FolderRow { owner, parent, name, role, remote: Option<id сервера> }`;
  `owner` — учётка или `Local`. Группа «На этом компьютере» в дереве — папки с `owner = Local`: локальные ящики и
  архивы.
- **Индексы** — те же, с числовыми ключами: `by_folder (FolderId, −дата, LetterId)`, `count`, `by_keyword`,
  `keyword_count`, `by_thread`, `recipients`. Разобранное тело (`body`: HTML, текст, список вложений) — производные
  данные по `LetterId`, их можно стереть и собрать заново воркером из `content`.
- **Маршрут команды** — по `letter_remote` (у какой учётки письмо), а не по префиксу ключа; у `Local` — без сети.

Почему не «перенос = перезапись ключа» (оставить `scoped` и переписать строки под ключ новой учётки): одна
транзакция тоже, но меняются id, которые держат интерфейс, выделение, поиск и задачи из писем (`mailtask`), а у
письма «только в базе» id сервера нет вовсе. Стабильный id нужен и IMAP (перенос папки сейчас переписывает ключи).

### 2. Содержимое — по хэшу, с дедупликацией

- **`content: Hash → ContentRow { skeleton, parts: Vec<PartRef>, refs: u32 }`** — письмо RFC 5322, у которого
  крупные листовые части (base64 и quoted-printable от 64 КиБ) вынуты и заменены ссылками на `part`.
  `Hash` — SHA-256 исходных байтов (`sha2` уже в сборке). Одинаковое письмо в двух учётках (копия себе, письмо в
  «Отправленных» и во «Входящих» общего ящика) хранится один раз.
- **`part: Hash → PartRow { bytes | chunks, refs: u32 }`** — раскодированная часть (вложение): одно вложение в
  50 пересланных письмах — одна запись. Больше 1 МиБ — кусками по 1 МиБ в `chunk: (Hash, n) → bytes`, чтобы
  запись redb не держала гигабайт одной страницей.
- **Точность байтов.** Скелет + части собираются обратно ровно в исходные байты: при записи ядро кодирует часть
  обратно (ширина строки, перевод строки, хвост) и сравнивает с исходным диапазоном; не совпало — часть остаётся в
  скелете как есть. Подпись S/MIME (`multipart/signed`) после сборки проверяется так же, как до. Зашифрованное
  (`application/pkcs7-mime`) не разбирается: один блоб.
- **Разбор MIME — в воркере** (CLAUDE.md «Чужие данные»): воркер отдаёт диапазоны листовых частей и их
  раскодированные байты (`MimeSplit`), ядро только кодирует обратно и сравнивает.
- **Счётчики ссылок и уборка.** `refs` растёт при записи письма и убывает при удалении; ноль — запись удаляется
  в той же транзакции. Отдельного сборщика мусора нет; проверка целостности (`refs` = числу ссылок) — тестом и
  командой диагностики.
- **Предел.** `MAX_CACHED_BLOB` (16 МиБ) для писем снимается: локальный архив должен хранить письмо целиком.
  Предел просмотра (`preview::MAX_INPUT`, 48 МиБ) не меняется.
- **JMAP — письмо целиком.** Тело письма JMAP загружается блобом `Email.blobId` и разбирается воркером, как у IMAP
  и EWS; `bodyValues` остаётся только превью строки. Трафик — тот же порядок (вложения и так качаются при
  открытии), зато у всех путей одна правда — байты письма (вопрос владельцу №3).

### 3. Перенос — одна транзакция

`Cache::move_letters(ids, to: FolderId) -> MoveTicket` — одна запись redb:
- `folders` строки, `by_folder`, `count`, `by_keyword`, `keyword_count` — как `move_email` сейчас, но пачкой;
- `content` и `part` не трогаются: тела и вложения не копируются;
- перенос в папку **той же учётки** — как сейчас: команда серверу (`Move`), сервер переносит сам;
- перенос в папку **другой учётки или в «На этом компьютере»** — `RemoteRef` источника помечается
  `detached` (синхронизация источника не возвращает письмо в старую папку, но видит удаление), строки задания
  пишутся в `outbound` той же транзакцией (п. 4).

**Замер** (2026-10-28, стенд владельца, release, redb 4, схема индексов как у `postman-cache`, 100 000 писем,
у части — по 1–3 ключевых слова, одна транзакция с записью задания на каждое письмо; скретч-крейт
`target/a-s8spec/mv`): перенос **1,4–2,4 с** в обычных прогонах (сборка транзакции 1,1–1,6 с, фиксация 0,24–0,87 с),
5,6 с при первом холодном прогоне; один прогон — 30 с, при параллельной сборке на том же диске (выброс, не норма).
Файл растёт на время транзакции (64 → 128 МБ: копии страниц, освобождаются после фиксации). Оценка для 1 млн
писем — 15–25 с: такой перенос идёт пачками по 100 000 (каждая — своя транзакция, в задании — общий номер), список
обновляется после каждой. Интерфейс не ждёт: транзакция — в потоке ядра, UI-поток видит итог событием.

### 4. Выгрузка на сервер — очередь по целевой учётке

После переноса в папку другой учётки строка над списком папки спрашивает (п. 5). Ответ — режим задания:

- **«Перенести на сервер»** — по каждому письму шаги, каждый записан в `outbound` и переживает перезапуск:
  1. содержимое есть в базе (нет — загрузить у источника: `Command::FetchRaw` → `content`);
  2. выгрузить в папку цели: JMAP — блоб на `uploadUrl` + `Email/import` (`mailboxIds`, `keywords`,
     `receivedAt`); IMAP — `APPEND` с флагами и датой (`UIDPLUS` → новый UID; без него — поиск по `Message-ID`);
     EWS — `CreateItem` с `MimeContent` в папку, `SaveOnly`, `PR_MESSAGE_FLAGS` без «черновика» и дата получения
     [проверить на Exchange 2013]. Между аккаунтами одного сервера JMAP — `Email/copy` с
     `onSuccessDestroyOriginal` (сервер переносит сам, без выгрузки);
  3. сервер подтвердил (id или UID) — новый `RemoteRef` цели, `place = Synced`;
  4. удалить у источника (`Destroy` пачками; у IMAP — `\Deleted` + `UID EXPUNGE`); снять `detached`-ссылку.
- **«Оставить локальным архивом»** — шаги 1 и 4: письмо целиком в базе (хэш сверен), затем удаление у источника;
  `place = Local`. Перенос в «На этом компьютере» — этот режим без вопроса.
- **Пределы и вежливость:** по одной очереди на целевую учётку, 1–2 одновременных выгрузки; пачки — до
  `maxObjectsInSet`/`maxCallsInRequest` JMAP, у EWS — до 20 писем и не чаще 5 запросов в секунду (правила S7 для
  боевого Exchange); `ErrorServerBusy`/429/`tooManyRequests` — пауза по ответу сервера; письмо больше
  `maxSizeUpload` (JMAP), `APPENDLIMIT` (IMAP) или предела Exchange — шаг «слишком большое», письмо остаётся
  локальным с пометкой, очередь идёт дальше.
- **Квота:** перед стартом и каждые 500 писем — `Quota/get` (JMAP, RFC 9425), `GETQUOTAROOT` (IMAP, RFC 9208);
  у EWS — по ошибке `ErrorQuotaExceeded` (проверка заранее — [проверить]). Места не хватит — задание на паузе
  строкой «На сервере нет места: осталось N писем · Продолжить · Оставить локально».
- **Повтор без дублей:** шаг 2 идемпотентен по записи в `outbound`: после сбоя на середине JMAP получает
  `alreadyExists` (если сервер не допускает дублей), IMAP и EWS — проверка по `Message-ID` в папке цели перед
  повтором.
- **Пауза, отмена, продолжение.** Пауза — очередь стоит, задание помнится. Отмена — строкой «Остановить перенос:
  готово 3 120 из 12 480 · Оставить остальные локально · Вернуть на место»: «Вернуть» — одна транзакция обратно в
  папку источника с прежними `RemoteRef` (у писем без своего содержимого — только так); «Оставить» — режим
  локального архива для оставшихся. Удаление у источника — всегда после подтверждения цели или сверки хэша.
- **Где живёт:** движок — `postman_core::migrate` (ядро функциональное), протокольные шаги — команды плагинов
  `Import`/`Copy`/`Destroy` (новая функция расширяет договор, ADR 0004). Своё: событие `Event::Migration { job,
  done, total, bytes, state }`.

### 5. Вопрос пользователю — в существующих приёмах

Без модальных окон (CLAUDE.md): нейтральная строка над списком целевой папки, как «Автоответ включён…»
(`docs/DESIGN.md` «Автоответ и квота»): «12 480 писем перенесены из «Stalwart · Входящие» · Перенести на сервер
«Exchange» · Оставить локальным архивом». Ход — в строке состояния, как квота: «Перенос: 3 120 из 12 480 ·
1,2 ГБ», щелчок — строка задания с «Пауза» и «Остановить»; конец — тост с итогом. В строке письма — значок
«ждёт переноса» / «только на этом компьютере». Вид и тексты — запрос в сессию дизайна (S8-D), до утверждения код
вида не пишется.

### 6. Миграция с формата 5

Сейчас данных «только в базе» нет, поэтому сбой миграции ничего не теряет:
- при первом запуске версии с форматом 6 — новый файл рядом (`*.redb.v6`), перенос строк из формата 5 в фоне со
  строкой «Обновление хранилища: N %» вместо списка (первый кадр не ждёт): каждой строке — `LetterId`,
  `RemoteRef` — из её ключа (`unscoped`, `profile_of`; IMAP — папка и UID из ключа; EWS — хэш `Id`), сырые письма
  из `blob` — в `content`/`part` через воркер, `body` — как есть по `LetterId`, задачи, S/MIME, состояния
  синхронизации — с новыми ключами;
- готово — замена файла переименованием, старый — `*.redb.v5.bak` до первого удачного запуска, затем удаляется;
  поиск — индекс пересобирается по `LetterId` в фоне (как при первом запуске);
- сбой — старый файл не тронут, новый удаляется, база формата 6 наполняется синхронизацией, как сейчас при смене
  формата (потерь нет: всё на сервере). В журнал — причина.

С формата 6 смена формата — только миграцией: открыть файл новее себя — отказ с понятным текстом, не удаление.

### 7. Шифрование хранения

С локальным архивом база — единственная копия писем. В 1.0 своё шифрование значений не вводим (вопрос №2):
- остаётся как сейчас: ACL профиля, BitLocker организации, письма S/MIME — только шифрованными;
- «Настройки → Безопасность»: строка «Диск с данными Postman не зашифрован BitLocker» с пояснением, если так
  [проверить, читается ли состояние без прав администратора: свойство оболочки `System.Volume.BitLockerProtection`];
- своё шифрование (ключ под DPAPI пользователя, AES-GCM на значение `content`/`part`/`body`, индекс поиска —
  отдельно) — отдельным решением после 1.0: цена — каждое чтение тела, индекс tantivy пришлось бы шифровать своим
  каталогом.

## Цена

- Самая большая переделка кэша с S4: ключи, маршрут команд, плагины JMAP, IMAP и EWS, индекс поиска, демо-ящик.
  Поведение синхронизации не меняется; тесты стенда — до и после.
- Размер `postman.exe` — почти без изменений (sha2 и base64 уже в сборке).
- Диск: дедупликация вложений обычно возвращает больше, чем стоят таблицы `remote` и `part`.
- Перенос 1 млн писем — пачками по 100 000 (п. 3).

## Откат

Формат 6 включается признаком сборки до приёмки S8: без него — формат 5 и одноразовый кэш. После приёмки отката к
формату 5 нет: старая версия базу формата 6 не читает. Письма локальных архивов выносятся экспортом (mbox, S8) или
переносом на сервер.
