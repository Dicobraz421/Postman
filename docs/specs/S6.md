## S6-01. Стенд: хранение задач и поручение

Тесты — `crates/core/tests/stand_tasks.rs` (user1…user3, за собой убирают; запуск — в шапке файла), находки —
`docs/STALWART.md` п. 37–42, пробелы — `docs/STALWART-GAPS.md` строки 34–44. Поля проверены по макетам «Задачи»,
«Поручил я», «Поручено мне» (срок и время, начало, «!», оценка, прогресс, статус, повтор, напоминание, проект,
категория, подзадачи, заметки, ссылка на письмо; исполнитель, наблюдатели, принял / в работе / готово / отклонил,
предложенный срок, причина отказа, история).

| Где хранить | Итог | Главное |
|---|---|---|
| JMAP Tasks (`urn:ietf:params:jmap:tasks`) | нет | не объявлен (тест заметит, если появится) |
| JMAP `CalendarEvent` с `@type: Task` | **работает** | создать, прочитать, изменить, удалить; `CalendarEvent/changes` у второго клиента; все поля карточки хранятся (п. 38); свои поля — `X-POSTMAN-*` через `iCalendar.properties`; отбор по сроку — на сервере, по статусу — нет (п. 39); поручение — iTIP сервера (п. 40). Нельзя: `recurrenceRules` (только `recurrenceRule`), `progressUpdated`, свойства поставщика |
| CalDAV VTODO | **работает** (то же хранилище) | `PUT`/`GET` как есть, `If-Match`, `sync-collection`, `calendar-query` по сроку и по STATUS; запись видна в JMAP как `Task`. Отдельный клиент и разбор .ics не нужны, пока хватает JMAP |
| FileNode (JSON) | работает, но хуже | файл виден и удаляем пользователем, нет отбора, iTIP и показа в других клиентах (п. 42, GAPS 15) |

**Поручение** (тест `delegation_round_trip`): `CalendarEvent/set` с участниками и `sendSchedulingMessages: true` —
копия сама у исполнителя (миллисекунды) и у наблюдателя; принять, «в работе» с процентом, «готово» — патч своей копии
с рассылкой, у поручившего PARTSTAT (IN-PROCESS, COMPLETED), STATUS и процент; новый срок — `SEQUENCE` + 1 у всех;
«забрать» — CANCEL (отказавшемуся — нет). Своё письмо iMIP REQUEST (тест `imip_request_by_mail_lands_in_calendar`)
сервер исполнителя разбирает так же — VTODO у него в календаре сам. Сервер **не** делает: COUNTER («предложить срок») — только письмо; COMMENT
в REPLY («причина отказа», «результат») — теряется; наблюдателю шлёт каждый шаг, а не итоги; письмо-приглашение —
шаблон сервера, не HTML Postman.

**Напоминания:** `alerts` хранятся; письмо сервер шлёт только по `action: email` относительно начала, по сроку задачи
— нет. Решение 7 в силе: напоминания — клиентом.

**Рекомендация для S6-02 (решение 1):** задачи — JMAP `CalendarEvent` с `@type: Task` (первый вариант решения 1
подтверждён стендом). Подробно:
- `TaskStore` над JMAP Calendars тем же `postman-jmap` (`CalendarEvent/get|set|changes`), без CalDAV-модуля; push —
  уже есть (`CalendarChanged`, тип `CalendarEvent`). CalDAV — только для проверок и совместимости.
- Задачи и события в одном календаре: календарь (`events`, сетка недели) отбирает `@type: Event`, модуль «Задачи» —
  `@type: Task`; отдельный календарь «Задачи» — по желанию [проверить: создать через `Calendar/set` и не показывать
  его в сетке — тогда отбор по `inCalendars`].
- Списки «Сегодня», «Выполненные», сортировка по сроку — по кэшу клиента (на сервере нет условий по статусу и
  сортировки по сроку, GAPS 35); с сервера — `CalendarEvent/changes` и окно по `after`/`before`.
- Поля Postman (проект, «Когда-нибудь», порядок подзадач, ссылка на письмо) — `X-POSTMAN-*` в `iCalendar.properties`
  (весь список — одним патчем); ссылка на письмо — ещё и `links` `mid:<Message-ID>` (видна другим клиентам как URL);
  подзадача — `relatedTo` с `parent`; повтор — `recurrenceRule`; дата выполнения — COMPLETED в `iCalendar` (сервер её не ставит).
- Поручение (решение 2, S6-09) — iTIP по VTODO, обе стороны в календаре сервера:
  - REQUEST («поручить», «изменить срок», «напомнить») — своим письмом iMIP (`EmailSubmission`: текст + HTML для
    людей без Postman + `text/calendar`, решение 3) при `sendSchedulingMessages: false`; сервер исполнителя кладёт VTODO
    в его календарь сам (тест `imip_request_by_mail_lands_in_calendar`). Письмо сервера («Invitation: …») — его
    шаблон, его не настроить. У поручившего — своя запись с той же UID, созданная без рассылки; применит ли сервер
    к ней REPLY исполнителя — [проверить в S6-09];
  - REPLY исполнителя (принял, в работе, готово, отклонил) и CANCEL — можно силами сервера (патч своей копии с
    `sendSchedulingMessages: true`), REPLY письмом сервер тоже применяет;
  - COUNTER («предложить срок») и комментарий шага («причина отказа», «результат») — только письмом, разбор в
    воркере: сервер их не сохраняет (GAPS 41, 42);
  - наблюдатели — [проверить в S6-09] не участниками iTIP, а письмом с итогом: участником (`ROLE=NON-PARTICIPANT`)
    наблюдатель получает каждый шаг (GAPS 40);
  - каждый шаг — письмо поручившему, в пороге входящих (GAPS 43, 4): шаги — только по действию человека.

Приёмка: тесты стенда — 8 из 8; раздел в `docs/STALWART.md`. Решения 1 и 2 приняты владельцем по рекомендации
(2026-10-22, `S0-decisions.md`).

## S6-02. Модель задач, хранилище, кэш

- Тип `Task` в `calendar` (L1, рядом с `Event`; JSCalendar Task: `title`, `due`, `start`, `progress`, `priority`,
  `recurrenceRule` (JSCalendar 2.0, не `recurrenceRules`), `alerts`, `relatedTo`, `participants`) ↔ VTODO; поля
  Postman (проект, «Когда-нибудь», ссылка на письмо, порядок подзадач, дата выполнения) — `X-POSTMAN-*` и COMPLETED
  в `iCalendar.properties` (решение 2; свойства поставщика JSCalendar Stalwart не принимает, `docs/STALWART.md`
  п. 38). Без I/O.
- `core::tasks` (L2): списки (Входящие — без срока и проекта; Сегодня — просроченные сверху; Предстоящие; Из почты;
  Когда-нибудь; Выполненные), проекты с прогрессом (выполнено / всего), категории — та же таблица, что у почты
  (`postman_core::categories`, S5-02 «б»).
- Хранилище — трейт `TaskStore`, реализация `JmapStore` (решение 1, 2026-10-22): `CalendarEvent/query` + `get`
  (отбор `@type: Task` — на клиенте, условия на сервере нет), `CalendarEvent/changes`, `set` без рассылки.
- Кэш: таблица задач в `cache` (новые таблицы создаются в старом кэше при открытии — без пересоздания), изменения —
  в потоке синхронизации: при входе и по push календаря (`CalendarEvent/changes`). Правка — в кэше сразу с пометкой
  «не отправлена» (интерфейс пишет её сам, `tasks::save_local` / `delete_local`, как правки писем, и шлёт
  `Request::Flush`), уходит на сервер сразу, а без связи — при её возвращении (очередь `link`) или после перезапуска; изменение уходит патчем к версии на сервере (поля, которые правил другой клиент, остаются его).

Сделано (PR): `postman_calendar::Task` (`task.rs`: JSCalendar ↔ модель ↔ VTODO, патч только изменений),
`postman_core::tasks` (списки, проекты, подзадачи, категории; `TaskStore`, `JmapStore`, `Request`/`Reply`,
`Command::Tasks` / `Event::Tasks`), таблицы `task` и `task_id` в кэше. Корпус VTODO — `crates/worker/tests/fixtures/todo-*.ics`
(Thunderbird, Apple «Напоминания», экспорт Outlook). Интерфейса нет — S6-05; демо-задачи — с S6-05 (снимки).

Приёмка: тесты модели (VTODO ↔ `Task` туда-обратно на корпусе: Thunderbird, Apple, экспорт Outlook), отбора по
спискам и прогресса проекта, миграции кэша; тест стенда `task_round_trip` (создать → у второго клиента через
изменения → выполнить → удалить).

## S6-03. Письмо ↔ задача

- Письмо со «Сроком» (`pm.due` + `pm.due.<ГГГГ-ММ-ДД>[t<ЧЧММ>]`, S5-04) — задача списка «Из почты»: представление
  над индексом ключевых слов кэша, без копии. Запись в хранилище появляется, только когда у такой задачи правят
  что-то кроме срока (заметки, подзадачи, проект), со ссылкой на письмо (`Message-ID` + `emailId`) — решение 4.
- Выполнение задачи снимает срок у письма (оба слова — одним `Email/set`, `sync::Command::Patch`); смена срока в задаче
  меняет его у письма и наоборот; снятие срока в почте закрывает задачу (решение 4).
- Из карточки задачи — «Открыть письмо» (письмо во вкладке, папка не меняется); у письма — метка срока, как сейчас
  (`lifecycle::badges`).

Приёмка: тесты связи (срок туда-обратно, выполнение → `keywords`, письмо удалено → задача без ссылки, не падает);
тест стенда `mail_due_is_task` (срок у user1 → задача; выполнить → слова сняты у второго клиента).

Сделано (PR): `postman_core::mailtask` — письма со сроком по индексу ключевых слов кэша (`letters`), задача-письмо
(`as_task`, UID `mail:<ключ письма>`, в хранилище не пишется — `tasks::save_local` её пропускает), «Из почты»
(`from_mail`: письма со сроком и записанные задачи поверх, без дублей), запись при правке не срока (`promote`:
ссылка — id письма и Message-ID, если тело загружено), правка задачи → патч слов письма (`letter_patch`: выполнение
снимает оба слова, смена или снятие срока — то же у письма; интерфейс шлёт его `Command::Patch`, как сроки S5-04),
сверка с почтой (`reconcile`: срок снят — выполнена, другой — срок письма, письмо удалено — без ссылки) — после
каждой сверки почты в потоке синхронизации (`tasks::Request::Reconcile`) и при загрузке задач. Ссылка на письмо в
задаче — `mid:` и/или `X-POSTMAN-EMAIL-ID` (без Message-ID — только id письма). «Открыть письмо» — `mailtask::letter_key`
для карточки (S6-06).

## S6-07. Повтор и напоминания

- Повтор (решение 8): каждый день, по будням, по неделе (дни), по месяцу (число), по году; «от срока» или «после
  выполнения через N»; хранение — `recurrenceRules` / RRULE. Выполнение повторяющейся — следующая копия со сдвигом.
- Напоминание: время из карточки, по умолчанию — из «Настройки → Календарь» (S5-20); срабатывает тостом и
  уведомлением Windows, если окно свёрнуто (решение 7); «Отложить на 10 мин / 1 ч / завтра» — в тосте. Планировщик —
  как у жизненного цикла писем (`lifecycle::plan`: один таймер к ближайшему сроку, без кадров между сроками).

Приёмка: таблица случаев повтора (31-е число, 29 февраля, смена часового пояса, «после выполнения»); тест
планировщика напоминаний (модель, часы подменяются); снимок `task-repeat`.

Сделано (PR): `postman_core::recur` — правило из `recurrenceRule` (каждые N дней, по будням, по неделе с днями, по
месяцу — число, по году) и «через N дней после выполнения» (`X-POSTMAN-REPEAT-AFTER`); прочее — «особое правило»
текстом. Следующий срок — от срока (31-е → последний день месяца, 29.02 → 28.02 в невисокосный год, «плавающее» время
— те же часы при смене пояса и перехода на зимнее время); выполнение повторяющейся — следующая копия (новый UID,
срок и начало сдвинуты), у выполненной повтора нет. Напоминания: `recur::plan` (сработавшие с прошлой проверки и
следующее — один таймер), «Отложить» (10 мин; час и завтра — в модели), тост с «Отложить на 10 мин», при неактивном
окне — уведомление Windows (WinRT, AUMID `Pets.Postman` в `HKCU\Software\Classes\AppUserModelId`). По умолчанию в
вариантах напоминания — из «Настройки → Календарь». Карточка: «Повтор» — варианты. Снимок `task-repeat`. Не сделано:
три варианта «Отложить» в тосте (у тоста pets-ui одна кнопка).

## S6-08. «Время в календаре»

- Кнопка в карточке: блок длительностью из задачи (по умолчанию — «Настройки → Календарь», S5-20) в ближайшее
  свободное окно своего календаря (`calendar::find_slots` по своей занятости и рабочим часам); ←/→ — соседние окна,

- Выполнение задачи — блок остаётся (было); удаление задачи — строка «Удалить и блок?» в карточке. Перенос блока в
  календаре меняет «запланировано» у задачи.

Приёмка: тест выбора окна (модель: рабочие часы, «вне офиса», граница дня); снимки `task-timeblock`,
`calendar-taskblock`; тест стенда `task_block_in_calendar`.

Сделано (PR): блок «Время в календаре» карточки (макет): оценка (по умолчанию — длительность из «Настройки →
Календарь»), ближайшее свободное окно своего календаря в рабочие часы (`find_slots`; сегодня, вечером — следующий
рабочий день, до недели), ‹ › и ←/→ — соседние окна, кнопка — поставить; полоса рабочего дня с занятостью, окном и

при удалении задачи.

## S6-09. Поручения в `core`

- Формат (решение 2): iTIP по RFC 5546 для VTODO — `METHOD:REQUEST` (поручить, изменить срок, вернуть с комментарием),
  `REPLY` (`PARTSTAT`: ACCEPTED, DECLINED, IN-PROCESS, COMPLETED — «готово, на проверку»), `COUNTER` (предложить срок),
  `CANCEL` (забрать); приёмка результата — `STATUS:COMPLETED` у поручившего и REPLY-итог исполнителю. Наблюдатели —
  `ATTENDEE;ROLE=NON-PARTICIPANT`, получают только итоги (решение 9). Письмо — `text/plain` + `text/html` для людей
  без Postman + `text/calendar` (как `calendar::imip_reply`).
- Приём: письмо с VTODO разбирает воркер; `core` сопоставляет по `UID` и `SEQUENCE`, ведёт ленту шагов (кто, что,
  когда, комментарий); устаревшие (`SEQUENCE` меньше) — пропуск с записью в журнал (как `invite::classify`, S5-11).
- «Напомнить» — повтор REQUEST без изменения `SEQUENCE` с пометкой в теле; не чаще раза в сутки (решение 10).
- Задача остаётся у поручившего до приёмки; у исполнителя — своя копия в «Мне поручили».

Приёмка: тесты автомата статусов (таблица переходов, недопустимые — ошибка), генерации и разбора iTIP на корпусе
(Thunderbird, экспорт Outlook); фаззинг нового входа воркера; тест стенда `delegation_round_trip` (user1 → user2:
принять → в работе → готово → принять результат; user3 — наблюдатель, получил итог).

## S6-10. Поручение на экране

- «Поручить» в карточке: исполнитель из справочника (поиск `AddressBook`, неверная раскладка), наблюдатели по
  желанию, срок, комментарий; отправка — Ctrl+Enter.
- У исполнителя — карточка как приглашение (раскладка Г1, S5-24): детали сверху, в строку «Принять» (заливка) /
  «Предложить срок» / «Отклонить» (тонированные, S5-19); дальше «В работе» → «Готово — на проверку». Та же карточка —
  над телом письма-поручения.
- У поручившего — лента шагов, «Напомнить», «Принять результат» (заливка) / «Вернуть с комментарием», «Изменить
  срок», «Забрать» (строка подтверждения).
- Статусы — круги 20 px: ждёт — серый точечный, принял — синий ✓, в работе — синий ▶, готово — зелёный ✓✓, отклонил —
  тёмно-серый ✕; предложенный срок — янтарной датой.

Приёмка: снимки `delegate` (форма), `delegation-in` (у исполнителя), `delegation-mail` (карточка в письме),
`delegation-steps` (у поручившего), `delegation-statuses` в обеих темах.

## S6-11. Раздел «Поручения» и «Ждём»

- Слева один пункт «Поручения»; над списком вкладки «Я поручил» | «Мне поручили»; на «Я поручил» флажок «Только свои»
  (по умолчанию стоит; снят — ещё и где я наблюдатель). Строка — исполнитель (или поручивший), круг статуса, срок,
  последний шаг.
- Быстрый фильтр «Ждём» (`postman_core::filters`, S5-03; слово `pm.wait`, S5-04) дополняется: письма-поручения по моим
  невыполненным поручениям (из «Отправленных», по `UID`); счётчик учитывает их без дублей с «Ждём ответа».

Приёмка: тест отбора вкладок и «Только свои»; тест «Ждём» на демо-ящике (поручение без приёмки — в фильтре, после
приёмки — нет); снимки `delegations-out`, `delegations-in`, `quick` (с поручениями).

Сделано (PR): модель раздела — `postman_core::assign` (`Tab`, `Bucket`, `section`, `counts`, `waiting_keywords`): «Я
поручил» — «На проверку», «В работе», «Ждут принятия» (отклонено, предложен срок, ждёт), «Только свои» снят — ещё и
где я наблюдатель (чип «наблюдаю», «поручил(а) …»); «Мне поручили» — «Новые», «В работе», «На проверке». Строка —
исполнитель (или поручивший) и последний шаг, предложенный срок — янтарём. Слева пункт «Поручения»: всего и бейдж
«ждут ответа + на проверку». «Напомнить всем» (и команда `task.remind_all`) — над «Ждут принятия», не чаще раза в
сутки каждому. Del — «Удалить поручение» (CANCEL исполнителю, у себя — удалить), «Забрать» — без строки
подтверждения: оба — тост «Отменить», письмо отмены сервер держит окно «Отменить» (`Release::After`, как отправка
письма), «Отменить» — копия как была, письмо не уходит (`Command::Withhold`: отмена отправки и удаление письма;
решение владельца 2026-10-22). «Ждём»: мои письма поручившего уходят со словом `pm.assign.<хеш UID>`
(`postman_calendar::assign::keyword`), фильтр берёт письма с ним по моим невыполненным поручениям
(`filters::Me::with_waiting`; на сервере — `hasKeyword`), письмо и с «Ждём ответа» — одно; внизу «Я поручил» —
«Невыполненные поручения (N) … — в быстрый фильтр «Ждём»» и «Открыть в почте». Снимки `delegations-out`,
`delegations-in`, `quick-wait` («Отправленные» с «Ждём»). «Невыполненные» — не на проверке у меня (готово ждёт моего
решения, а не исполнителя; решение владельца 2026-10-22, по макету — решение 12); тест: в работе — в фильтре, готово и
после приёмки — нет. Не сделано: «Напомнить всем» — письмом (решение 10), не «без письма» макета.
