# Предложения в gpui-fast (longbridge/gpui-fast) — черновик

> **Не опубликовано.** Публикация — issue или PR в чужом репозитории, только с согласия владельца. Перед отправкой
> перевести на английский и сверить с последней версией gpui-fast.
> Сверено с **gpui-fast-windows 0.1.13** (crates.io). Источник правок — `pets/crates/pets-gpui-windows`
> (ревизия `4ac64b9`) и его `README.md`. Контекст — `docs/decisions/2026-11-08-gpui-fast-architecture.md`.

## Уже есть в 0.1.13 — не предлагаем

- **Кадры по запросу.** У нас поток vsync спит без запросов кадра: раньше он будил все окна на каждом обновлении
  экрана, это ~3 % CPU в простое. У них то же самое: `fast/frame_schedule.rs` (0.1.11, #84), с пробуждением по
  уведомлению об устройстве, плюс #85 (0.1.13) — без лишних запросов после ввода. Нашу правку убираем.
- **Шейдеры в exe** (`D3DCompile` в `build.rs`) — не предлагаем.
- **`gpui_windows::pets`** (OLE drag source, значки из ресурса, снимок окна, уведомления) — API наших приложений,
  не платформы. Не предлагаем.

## Платформа Windows (`gpui-fast-windows`)

### 1. Живой ресайз: кадр на `WM_SIZE` внутри цикла перетаскивания
- **Проблема.** Пока тянут край окна, Windows крутит модальный цикл. Кадр нового размера рисуется по таймеру цикла
  (`USER_TIMER_MINIMUM`, ~15,6 мс) или по `WM_PAINT`, который мышь откладывает. Содержимое отстаёт от рамки, в новой
  области — чёрная полоса. У swapchain окна (`CreateSwapChainForHwnd`) стоит `DXGI_SCALING_NONE`, поэтому пока кадра
  нет, DWM показывает новую область чёрной.
- **Замер.** `resize-check.ps1` (доля чёрных пикселей при разворачивании, `SetWindowPos`, «с экрана»), глазами при
  перетаскивании края и угла. До правки — чёрная полоса на каждом шаге, после — нет. Числа p99 ресайза — FAST-2.
- **Суть.** Флаг «в цикле» между `WM_ENTERSIZEMOVE` и `WM_EXITSIZEMOVE`. Внутри цикла `WM_SIZE` сразу рисует кадр
  (вне цикла нельзя: `WM_SIZE` от `Window::resize` приходит, пока приложение занято). Swapchain окна создаётся с
  `DXGI_SCALING_STRETCH`: пока нового кадра нет, DWM растягивает прошлый. DirectComposition по умолчанию выключена
  только у нас (непрозрачный фон), это не предлагаем.
- **Файлы.** `events.rs`, `window.rs`, `directx_renderer.rs`, `platform.rs`.

### 2. Цвет новой области при ресайзе
- **Проблема.** Пока swapchain не показал кадр нового размера, DWM показывает GDI-поверхность окна. Её стирает
  `WM_ERASEBKGND` (синхронно из `SetWindowPos`) кистью класса, а кисть чёрная. На светлой теме справа и снизу видно
  чёрное поле.
- **Замер.** Ручная проверка Урфина 2026-10-23 (чёрное поле при перетаскивании края), `resize-check` — доля чёрного.
- **Суть.** Из каждого кадра берётся цвет фона: первый сплошной непрозрачный квад во всё окно, то есть `bg` корня.
  `WM_ERASEBKGND` заливает этим цветом. До первого кадра — прежняя чёрная кисть.
- **Файлы.** `events.rs`, `window.rs`.

### 3. Окно без чёрного кадра на старте
- **Проблема.** До первого Present окно показывает чёрную кисть класса.
- **Замер.** Postman: 80–200 мс чёрного окна → 0 (Windows Graphics Capture с первого кадра, `start-probe`).
- **Суть.** Окно скрыто DWM (`DWMWA_CLOAK`) с создания до первого кадра, который GPU доделал и DWM забрал: запрос-событие
  и `DwmFlush` после Present. Если показывать сразу после Present, на один vsync всё равно видно чёрный кадр.
- **Файлы.** `window.rs`, `directx_renderer.rs` (`wait_frame_composed`).

### 4. Ленивые промежуточные текстуры путей
- **Проблема.** Текстуры путей (обычная + MSAA 4×, размером с окно, 5 поверхностей) создаются при создании
  рендерера и пересоздаются на каждом ресайзе, хотя в большинстве кадров путей нет. На встроенной GPU это память
  процесса.
- **Замер.** 1600×1000: ~33 МБ на окно без путей; на ресайзе остатки не копятся. Тест `lazy_path`: путь рисуется в
  скрытом окне через `render_to_image`, пиксели проверяются до и после ресайза.
- **Суть.** `path_textures: Option<PathTextures>`: текстуры создаются в первом кадре с путями и сбрасываются на ресайзе.
  В `fast/frame.rs` цели путей берутся, только если они есть: `PathTargets::of` возвращает `Option`, `draw_batches`
  создаёт текстуры при `!scene.paths.is_empty()`.
- **Файлы.** `directx_renderer.rs`, `fast/frame.rs`.

### 5. Принудительный WARP: `GPUI_FORCE_WARP=1`
- **Проблема.** На виртуальных машинах, по RDP и при сбойном драйвере нельзя явно выбрать программный Direct3D:
  перебор адаптеров берёт первый попавшийся.
- **Замер.** Нет: это диагностика, не скорость. Тест `force_warp`.
- **Суть.** При `GPUI_FORCE_WARP=1` устройство создаётся на адаптере `EnumWarpAdapter` (фабрика `IDXGIFactory6`), без перебора GPU.
  Переменная читается раз за процесс, после потери устройства оно пересоздаётся тоже на WARP. Сочетается с их
  восстановлением устройства (#93, 0.1.13).
- **Файлы.** `directx_devices.rs`.

### 6. Быстрый `layout_line` для простых строк
- **Проблема.** Каждая строка проходит через `IDWriteTextLayout`, даже ASCII или кириллица без лигатур: ~40 мкс на строку.
  В длинных списках (почта, файлы) это заметная доля работы UI-потока за кадр прокрутки.
- **Замер.** 5 мкс вместо 40 на строку. Результат побитно равен старому пути на корпусе строк (тесты `pets_fast_*`,
  сводка — с `--nocapture`).
- **Суть.** Простая строка (ASCII, Latin-1, кириллица, пунктуация) собирается из таблицы глифов по (шрифт, размер).
  Шрифты с лигатурами, контекстными заменами и кернингом отсекаются разбором GSUB/GPOS/`kern`, остальное идёт старым
  путём. В 0.1.13 добавлено деление строки по разделителям Unicode (`layout_line_without_separators`), быстрый
  путь встаёт внутрь него.
- **Файлы.** `direct_write.rs`, `direct_write/fast.rs`, `direct_write/fast_tests.rs`.

## Пакеты и версии

### 7. gpui-pre необязателен при фиче `gpui-fast` (gpui-kit, gpui-base, gpui-component, gpui-kit-assets)
- **Проблема.** В gpui-kit 0.7.3 и 0.9.0 `gpui = gpui-pre` и `gpui_platform = gpui-pre-platform` обязательны и
  закреплены точно (`=0.3.9`, `=0.3.11`). С фичей `gpui-fast` код идёт через `gpui_fast` (`extern crate gpui_fast as
  gpui`), но собираются оба семейства. Последствия:
  - два ядра и две платформы Windows в сборке: время сборки, возможно и размер exe (размер — FAST-2);
  - непатченный gpui-pre-windows в release ищет fxc.exe (`panic!("Failed to find fxc.exe")`). Приходится держать
    `[patch]` на платформу, которой приложение не пользуется;
  - точные версии gpui-pre ограничивают gpui-fast. При gpui-kit 0.7.3 ядро не поднимается выше 0.1.11: у 0.1.12+
    вспомогательные снимки закреплены на `gpui-pre-* =0.3.10/0.3.11`.
- **Суть.** В gpui-kit, gpui-base, gpui-component и gpui-kit-assets сделать `gpui`/`gpui_platform` (gpui-pre)
  `optional` под фичей по умолчанию (например `gpui-pre`). Тогда `default-features = false, features = ["gpui-fast",
  …]` собирает одно ядро.
- **Файлы.** `Cargo.toml` четырёх крейтов, `cfg` в `lib.rs` (там, где сейчас `cfg(feature = "gpui-fast")`).

### 8. Точные версии внутри семейства, свободные — на чужие крейты
- **Проблема.** Внутри семейства зависимости свободные: `gpui-fast-windows` 0.1.11 → `gpui-fast = "^0.1.11"`,
  `gpui-fast` 0.1.11 → `gpui-fast-macros = "^0.1.11"`. В `Cargo.lock` при ядре 0.1.11 (и даже 0.1.7) макросы встают на
  0.1.13, а снимок платформы при обновлении уезжает от ядра. На чужой крейт, наоборот, стояло `=`:
  `gpui-fast-macos` 0.1.7 → `cocoa = "=0.26.0"`. Из-за этого ядро нельзя было закрепить на 0.1.7 (версия снимка в
  первом опыте): в `Cargo.lock` уже была cocoa 0.26.1, нужен откат во всём дереве. Это macOS-крейт, но он
  разрешается и в сборке только для Windows. В 0.1.11 macOS перешёл на objc2, конкретно эта проблема ушла.
- **Суть.** Свои крейты семейства — `=` (как у gpui-pre), чужие — `^`. Платформа, макросы и ядро одной версии
  всегда идут вместе.
- **Файлы.** `Cargo.toml` крейтов `gpui-fast-*`, `release.toml`.
